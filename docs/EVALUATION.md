# 檢索評估

以 [TIPO 種子集](../evaluation/tipo_seed.json) 及 [評估腳本](../scripts/evaluate_search.py) 比較詞彙、向量與混合加重排序。種子集有四筆查詢與五項相關標註，由 Codex 核對已索引的官方標題或請求項，待人工複核。公開與公告分開評分。同一文件階段和編號的其他版本保留原排行位置，重複命中只計分一次。

- Precision@10 採保守下限，分母固定為 10，未標註項與空位皆不計分。
- Recall@10 與 nDCG@10 只對已標註池計算。未標註文件另列數量，不能據此判為不相關。
- MRR 取首個已知相關文件的倒數排名。標註值 0、1、2 分別表示不相關、部分相關、直接相關。
- 延遲以本機 HTTP 往返計時，包含服務、資料庫及模型。每個模式的 P95 採 nearest rank，少量重複的結果不代表負載上限。
- 原文核對另以 `evaluate_citations.py` 驗證指定版本、字元區間、逐字引文、XPath 及雜湊。硬體耗電及每次查詢成本未量測。

將 `--dataset` 指向人工複核後的同格式資料集即可重跑。應記錄語料批次、標註者、判定依據及模型版本。

## 2026-11-09 引文核對

執行 `python scripts/evaluate_citations.py --api http://127.0.0.1:18022`。測試涵蓋電阻量測、光硬化樹脂、廢水監控及醫療影像標定。六個 TIPO 文件版本包含公開全文、同案公告請求項與只有書目的版本。共 12 個判定，5 段輸出引文均與同版本的原文、字元區間、XPath 及來源檔雜湊一致。其餘判定未輸出引文，涵蓋不存在的測試字串及書目資料不足。

初次執行的 5 段引文均來自請求項。另在 `202639611` 加入只出現在說明書的測試特徵「可將長波長光轉換為短波長光」。評估腳本先核對該文字存在於說明書且未逐字出現在請求項，再要求模型回傳發明內容段落引文。引文是否足以支持更廣泛的技術判定，以及跨案例召回，仍需另外驗證。

擴充後共 7 次比對、14 個判定，6 段引文全部核對成功。新案例定位至 `/invention-specification/description/disclosure/p[2]`，區間 `[0, 62)`。另用 `verify_document 202639611` 從存檔 XML 重驗 19 項請求項和 122 個說明書段落。

## 人工複核候選池

[歷史待複核候選池](../evaluation/tipo_review_pool.json) 紀錄 2026-11-09 的候選。新版候選由各模式前十名的聯集與種子已知文件構成，依文件階段與編號去重。程式重新查同編號的資料庫版本，挑選可取得的最完整版本，即使原本命中的是書目。供複核使用的清單省去模式、順位與預設分數。

2026-11-09 以四案各跑一次，產生 35 組查詢與文件配對。五項種子相關標註皆被各模式找回。詞彙、向量、混合加重排的 P50 分別為 29.58、432.43、20,544.74 ms，nDCG@10 分別為 0.980、0.888、0.815。這是同一批小樣本的暫定標註結果，不能外推至其他資料庫或查詢。

複核時先複製新版候選池，逐筆核對文件。可用 `document_id` 讀取同一語料庫的詳情與請求項。重建資料庫後，評估器依 `stage`、`number`、`content_scope`、`document_sha256` 與 `parser_version` 核對相同內容，即使 UUID 已更換。歷史候選池缺少版本指紋，需要重建候選池後再複核。

每筆 `grade` 填 0（不相關）、1（部分相關）或 2（直接相關），在 `basis` 寫下判定依據，能定位時附請求項號或段落。若資料不足，可先保留空值。全池確認後填入 `reviewer`，將 `label_status` 改為 `human_reviewed`，以 `--dataset` 指向複核檔重跑。評估器要求每案至少有一項相關文件才能計算召回率。指標衡量是否找回指定階段的文件號，證據完整性另由引文驗證衡量。

可用新檔名重建候選池，避免覆寫既有人工紀錄。

```powershell
python scripts/evaluate_search.py --api http://127.0.0.1:18022 --review-pool evaluation/tipo_review_pool_next.json
```

## 2026-11-26 PostgreSQL 查詢計畫基線

在隔離 PostgreSQL 16.14／pgvector 0.8.2 資料庫，將固定官方種子的公開資料回存並執行 `ANALYZE`。以 API 執行角色在唯讀快照中量測 117 個文件版本、1,560 個詞彙片段（不含完成標記）及 1,624 個向量。每個 SQL 先預熱一次，再執行七次。下表是 PostgreSQL 執行時間，單位毫秒。它與含模型、HTTP 的延遲量測分開計算。

| 案例 | 詞彙 P50／P95 | 向量 P50／P95 | 原向量寫法 P50／P95 | 向量候選 |
| --- | ---: | ---: | ---: | ---: |
| 動態導通電阻，不限 IPC | 0.613／0.774 | 7.202／7.925 | 同左 | 100 |
| 動態導通電阻，G01R27/02 | 0.647／0.704 | 0.807／0.814 | 1.052／1.151 | 4 |
| 光硬化性樹脂組成物，C08F2/48 | 1.303／1.328 | 1.038／1.167 | 1.722／3.232 | 1 |

兩組精確 IPC 案例的新舊結果逐筆相等，包含順序及分數。精確分類先縮小文件範圍，再用 `patent_dense_chunks_pkey` 取得向量，兩例的密集索引節點分別為每次平均 20 筆、4 次迴圈，以及 157 筆、1 次迴圈。原寫法在兩例都掃描全部 1,624 向量。不指定 IPC、或指定四碼 IPC 子類時，仍採全域計畫。最終詞彙計畫使用 `ix_patent_lexical_terms`。另一輪同一小語料曾選擇順序掃描，不能保證 PostgreSQL 固定選用 GIN。

重現時，依 [測試文件](TESTING.md) 重建官方隔離語料，設定 PG 與已索引的嵌入模型，再執行：

JSON 保留計畫名稱、使用的索引、節點實際筆數、記憶體／磁碟區塊計數及計時，省略 SQL 條件與嵌入常數。樣本適合比較兩種 SQL 的候選掃描及結果等價，尚未驗證大量或未預熱語料，也未證明整體模型搜尋更快。

### HTTP 併發結果
